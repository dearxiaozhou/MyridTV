## 一、事实底座（全部实测，非推测）

**主文件顶层状态**：137 个 `let/var`，分四类：
| 组 | 数 | 代表 | 写特征 |
|---|---|---|---|
| 核心画布态 | 3 | canvas / nodes / settings | settings 整写25+属性写68+读332（读写之王） |
| 选中态 | 3 | selectedId / selectedIds / selectedImage | 整写 27-41 次（高频重写） |
| Agent/配置态 | 28 | canvasAgent* 全族 | 多数整写≤6 次 |
| 交互/任务态 | 35 | dragState/portDragState/cropState/*Timer/*Cache | 典型 null↔对象 整写 |

**已被验证的通道**（十刀实战）：模块读主文件态走 `D("x")` getter 注入，块内整写走 `setX` 双通道——已有 29 个符号被 5-1 个模块这样消费，无一例运行时事故。

**分类修正**（重要）：早先"待攻巨石"里 `smChainModeProbe 368行 / startCanvasMiddlePan 222行` 是**分块误差**——实为 21 行纯读谓词函数 + 顶层事件句柄赋值混排。真实结构：交互域 = 若干小纯函数 + 一张 `window.onmousemove` 巨型顶层句柄网。**剩余块的墙不是函数体积，是顶层句柄对状态网的平铺访问。**

## 二、方案选型

### 否掉的：全局 Store 大重构（redux 化）
settings 读 332 处、nodes 读 153 处——全量改 `store.get/set` 要动 ~500 个引用点，
一步登天 = 一次不可回归验证的大爆炸，违背"每次改一处并验证"的纪律。拒绝。

### 采纳的：三层渐进「状态存取层」（Strangler 模式，零大爆炸）

**L1 · 快照访问器模块（新增，~80 行，无行为变化）**
`canvas-state-hub.js`：把 137 个顶层状态按上表分组，提供
- `get(key)`：统一读口（内部仍指主文件真变量，configure 注入 getter 表，沿用 D() 已验证机制）
- `set(key, value)`：统一整写口（含写后钩子位：scheduleSave/render 的联动**先不接**，只留接口）
- `keys()`：调试自省
L1 不迁任何声明、不改任何现有读写点——它只是把十刀散落的 `configure({x: () => x, setX: v => {x = v}})` 注入表**收拢成一个注册表**，为 L2 提供单一消费面。

**L2 · 整句柄迁移（逐域，每刀≤150 行）**
剩余大块的钥匙从「函数搬移」换成「**句柄搬移**」：
- 目标顺序（读面从小到大）：Agent/配置态句柄域（28 个状态整写≤6，最易）→ 交互/任务态的 *State/*Drag 域（状态随域自持先例=第九刀 redirectPickMode）→ 选中态 → settings/canvas/nodes 核心三角（最后，读面最大，只迁"写口集中"的段落）。
- 每刀公式不变：动态边界 + string_spans 感知替换 + 纯度三证 + CDP 功能真跑 + 完整 pre-commit。
- 顶层句柄（如 window.onmousemove）改法：主文件留一行 `CanvasInteractionHub.onMouseMove(e)` 转发，句柄体入模块，句柄内所有状态读写走 hub 的 get/set（L1 消费面）。

**L3 · 写后联动收敛（可选，远期）**
把散落 200+ 处的「改完 render()+scheduleSave()」手工三连，收进 hub 的写后钩子；
只有在 L2 完成 80% 句柄迁移后才做，避免双写路径。

## 三、风险与护栏
1. **回归护栏已就位**：60 e2e + verify.ps1 门禁 + CDP 功能真跑配方（第九刀范式：临时态自清）。
2. **双读口风险**：L2 迁移中同一变量既被模块 getter 又被 hub get 读——值同源（都指真变量），可接受；禁止的是双**写**源，hub.set 与直写并存时逐点消灭。
3. **打包投递**：新模块必须进 STATIC_PATCHES + html 双登记（A 线已证明该链在隐私门禁下健康）。
4. 每层完成判据：主文件行数下降 + `D("` 注入表项收敛进 hub 注册表 + 十刀台账继续逐刀登记。
